# Recipes

Recipes are small, complete compositions of the design system's components for situations that come up in every product. Each one is tested (behavior, keyboard flow and axe), has stories you can try, and has a doc whose code block is the recipe's source file. Copy a recipe, replace the sample data and the server calls, and keep the structure: the order of controls, the focus handling and the wording are the point.

Agents: start from a recipe when one fits (`get_recipe` in the MCP server returns the same docs from `docs/recipes/`), then run `validate_snippet` on what you produce.

Every recipe assumes one `ToastRegion` near the root of the app, inside `DSProvider`.

## How they stay true

- Each recipe imports only what the package exports (`loui-ds`, `loui-ds/patterns`); the doc shows those imports.
- `docs/recipes/*.md` embeds the recipe's `.tsx` file between two markers. `pnpm exec tsx src/recipes/sync.ts` rewrites the block and `src/recipes/docs.test.ts` fails when it is stale.
- The tests run the keyboard flow and axe on every state, with fake timers where the Undo window matters.

## Principles you will see repeated

- Deleting always asks, in a dialog that names the object and the consequence, with focus on Cancel. An Undo toast follows.
- Reversible actions never ask; they offer Undo.
- One primary action per screen, at the top right, with a shortcut.
- Lists are alphabetical by default; empty states say what happened and what to do.
- Anything that reaches a customer waits for approval.
