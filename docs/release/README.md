# Release process

Loui DS is published on npm as `loui-ds` under the MIT license (ADR-0004, amended 2026-11-03). Pushing a version tag publishes it; nothing is published from a laptop.

## Two changelogs, on purpose

- Root [`CHANGELOG.md`](../../CHANGELOG.md): the **task log**, hand-maintained under `[Unreleased]` (AGENTS.md rule 2). It records every finished TODO task with its ID.
- `docs/release/CHANGELOG.md`: the **release notes** that consumers read, generated by Changesets from `.changeset/*.md`.

Changesets always writes `CHANGELOG.md` next to `package.json`, which would overwrite the task log. `pnpm changeset:version` therefore runs `scripts/release/version.mjs`, which sets the task log aside, runs `changeset version`, moves the generated section into `docs/release/CHANGELOG.md`, restores the task log and renames its `[Unreleased]` heading to `[x.y.z] - date`. Never run `changeset version` directly.

The root package is listed in `pnpm-workspace.yaml` (`'.'`) because Changesets only sees workspace packages.

## Flow

1. **With every user-visible change** (anything in `src/`, tokens, `exports`, docs consumers rely on), run `pnpm changeset`, pick the bump per the [versioning policy](./versioning.md) and write one or two sentences for a consumer: what changed and what to do. Commit the generated `.changeset/*.md` with the change. Pure internal work (tests, CI, refactors without API or visual effect) needs no changeset.
2. **Before a release** run `pnpm check:ci`, `pnpm examples:verify`, `pnpm publint`, `pnpm attw` and `pnpm size` (CI runs them on every pull request). `pnpm api:check` is part of `check:ci`: an API change must come with an updated `api/*.api.md` (`pnpm api:update`) that a reviewer has read.
3. **Cut the version:** `pnpm changeset:version` on a branch. Review `package.json`, `docs/release/CHANGELOG.md` and the root `CHANGELOG.md`, then merge.
4. **Tag:** `git tag v<version>` on the merge commit and `git push origin v<version>` (`privatePackages.tag` is `false` in `.changeset/config.json`; tag by hand).
5. **GitHub Release (automatic):** the tag starts `.github/workflows/release.yml`. It checks that the tag matches `package.json`, builds, runs `publint`, `attw` and `size`, packs `loui-ds-<version>.tgz`, publishes it to npm with provenance through npm Trusted Publishing and creates the Release with the notes of that version from `docs/release/CHANGELOG.md` plus the install command. Tags with a hyphen (`v1.0.0-next.0`) become pre-releases. Consumers install with `pnpm add loui-ds`.
6. **npm authentication:** Trusted Publishing (OIDC). On npmjs.com, `loui-ds` › Settings › Trusted Publisher trusts GitHub Actions for `xrazai/loUI` and the workflow file `release.yml`; there is no npm token or repository secret. Renaming the workflow file or moving the repository breaks publishing until that setting is updated. The trusted publisher must allow `npm publish` (not only `npm stage publish`). To retry a failed release, run the Release workflow by hand (Actions › Release › Run workflow) with the tag, or `gh workflow run release.yml -f tag=v<version>`; steps already done are skipped. The 0.2.0 publish used a short-lived token, which was then removed.

## Pre-1.0 channel

While the major version is `0`, minor releases may contain breaking changes (see the policy) and every component starts `experimental`. `1.0.0` is cut when the core set of components has graduated to `stable` (see the lifecycle) and the support matrix (ADR-0009) has held for a full release cycle. Pre-releases (`1.0.0-next.0`) use `pnpm changeset pre enter next` and `pnpm changeset pre exit`.
